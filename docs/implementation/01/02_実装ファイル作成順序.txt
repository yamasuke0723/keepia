Keepia 認証・認可基盤　実装ファイル作成順序
==============================================

1. この文書の目的
------------------

この文書は、分割済みのコード・設定ファイル44個を、依存関係で迷わない順番に
自分の手で入力するための実装順序表である。

基本仕様書は設計内容を機能別に説明しているため、説明の登場順と、実際にJava
ファイルを作る順番は必ずしも一致しない。

たとえばTenant.javaはTenantStatusを使用するため、実装時は次の順番になる。

1) TenantStatus.javaを作る。
2) Tenant.javaを作る。

同様に、SecurityConfig.javaは多数のクラスを組み立てる設定クラスなので、
関連クラスをすべて作った後、production Javaの最後に作る。


2. 実装時の基本ルール
----------------------

・この資料フォルダからKeepia本体へファイルを一括コピーしない。
・各ファイルの内容を確認しながら、自分の手で1ファイルずつ入力する。
・package文、import文、アノテーション、修飾子、Javadocも省略しない。
・Entityのフィールドはprivateのまま入力する。
・V1～V5のSQLファイルは変更しない。
・コンパイルエラーが出た場合、後続ファイルを先に増やさず、その工程内で解消する。
・各工程の確認が成功してから次の工程へ進む。


3. 作業開始前
--------------

この工程ではまだファイルを作らない。

1) mainブランチにいることを確認する。

   git branch --show-current

2) 未コミット変更を確認する。

   git status

3) 実装ブランチを作る。

   git switch -c feature/authentication-foundation

4) 現在のテスト結果を確認する。

   .\mvnw.cmd test

既存テストが失敗した場合は、今回の実装前からの失敗として記録する。


4. 工程1　列挙型を作る
----------------------

Entityより先に、Entityのフィールド型として使用するenumを作る。

作成順1
src/main/java/jp/keepia/domain/TenantStatus.java

役割：
保守会社の状態をACTIVE、STOPPEDとして定義する。
Tenant.javaのstatusフィールドがこの型を使用する。

作成順2
src/main/java/jp/keepia/domain/CustomerStatus.java

役割：
顧客の状態をACTIVE、STOPPEDとして定義する。
Customer.javaのstatusフィールドがこの型を使用する。

作成順3
src/main/java/jp/keepia/domain/UserRole.java

役割：
OPERATOR、ADMIN、STAFF、CUSTOMERを定義する。
AppUser、AccountPrincipal、AccessScope、AccessPolicyが使用する。

作成順4
src/main/java/jp/keepia/domain/UserStatus.java

役割：
利用者の状態を定義する。
AppUser.javaのstatusフィールドがこの型を使用する。

工程1の確認：

   .\mvnw.cmd -DskipTests compile

この時点で後続クラスがまだ存在しないことによるエラーは発生しない。


5. 工程2　Entityを作る
----------------------

enumを作成した後、DBのテーブルへ対応するEntityを作る。

作成順5
src/main/java/jp/keepia/domain/Tenant.java

先に必要なファイル：
TenantStatus.java

対応テーブル：
tenants

作成順6
src/main/java/jp/keepia/domain/Customer.java

先に必要なファイル：
CustomerStatus.java

対応テーブル：
customers

作成順7
src/main/java/jp/keepia/domain/AppUser.java

先に必要なファイル：
UserRole.java
UserStatus.java

対応テーブル：
app_users

作成順8
src/main/java/jp/keepia/domain/LoginRateLimit.java

対応テーブル：
login_rate_limits

工程2の確認：

   .\mvnw.cmd -DskipTests compile

確認すること：

・importエラーがない。
・EnumType.STRINGを使用している。
・DBの列名と@Columnのnameが一致している。
・Entityのフィールドがprivateになっている。
・JPA用コンストラクタがprotectedになっている。

依存先：

依存先：

作成順12
src/main/java/jp/keepia/repository/LoginRateLimitRepository.java

依存先：
LoginRateLimit.java

注意：
LoginRateLimitRepositoryにはPostgreSQLのON CONFLICTを使用する処理がある。
login_rate_limits.key_hashに一意制約または一意インデックスが存在することを、
V1～V5の定義で確認する。既存SQLはこの段階では変更しない。

工程3の確認：

   .\mvnw.cmd -DskipTests compile


7. 工程4　認証設定値と小さな共通クラスを作る

作成順15

先に必要なファイル：
AppUser.java
UserRole.java

役割：
Spring Securityが保持する認証済み利用者情報を表す。
認証後はeraseCredentials()でパスワードハッシュを消去する。

作成順16

先に必要なファイル：

役割：

作成順17

先に必要なファイル：

役割：

工程4の確認：

10. 工程7　ControllerとSecurityConfigを作る
------------------------------------------

すべての認証部品が作成できた後、画面Controllerと組み立て設定を作る。

作成順25
src/main/java/jp/keepia/account/AccountController.java

先に必要なファイル：
AccountPrincipal.java

作成順26
src/main/java/jp/keepia/config/SecurityConfig.java

作成を最後にする理由：
SecurityConfigはAccountUserDetailsService、各Handler、各Filter、Repository、
SecurityPropertiesをまとめてSpring Securityへ登録するためである。
先にSecurityConfigを入力すると、未作成クラスによるコンパイルエラーが大量に出る。

工程7の確認：

   .\mvnw.cmd -DskipTests compile

ここまで成功すれば、production Java 26ファイルの入力が完了している。

17. 最終テスト実行順序
----------------------

テスト用PostgreSQLと次の環境変数を準備する。

・KEEPIA_TEST_DB_URL
・KEEPIA_TEST_DB_USER
・KEEPIA_TEST_DB_PASSWORD

1) コンパイルを確認する。

   .\mvnw.cmd clean test-compile

2) 全テストを実行する。

   .\mvnw.cmd test

3) 成功後に差分を確認する。

   git status
   git diff --check

4) V1～V5が変更されていないことを確認する。

5) ブラウザで次を手動確認する。

・ログイン画面を表示できる。
・正しいメールアドレスとパスワードでログインできる。
・誤った資格情報では共通エラーを表示する。
・ログアウトできる。
・停止利用者と停止所属先を拒否できる。
・権限不足時に403画面を表示する。
・ログイン失敗上限到達後に一時ブロックされる。
