======================================================================
Keepia 実装①「起動・DB・認証」手動テスト手順書
======================================================================

1. この手順書の目的
    実装①「起動・DB・認証」について、ブラウザ上の操作と画面表示を
    確認します。Eclipse、DBeaver、ブラウザを使って実施します。

    対象
        ・ログイン画面の表示
        ・正しい資格情報でのログイン
        ・誤った資格情報に対する共通エラー
        ・ログアウト
        ・停止利用者、停止所属先の拒否
        ・403画面の表示
        ・ログイン失敗上限到達後の一時ブロック

    実施範囲の補足
        現時点では、実際の権限別業務URLが未実装のため、権限不足から
        403画面に至る経路は手動確認できません。MT-06では403画面の
        表示とHTTPステータスを確認します。
        権限別URLへのアクセス制御は、自動テストで確認済みです。


2. 事前準備

    2.1 使用するデータベース
        通常起動用の keepia を使用します。
        keepia_test は自動テスト用のため、今回は使用しません。

        以下のSQLは、この手順書専用のデータを登録・変更します。
        実際の利用者や所属先のデータは使わず、記載した対象だけを
        操作してください。

    2.2 Eclipseで通常のアプリケーションを起動する
        (1) メニューの「実行」→「実行の構成」を開きます。

        (2) 左側の「Spring Bootアプリケーション」から
            「keepia - KeepiaApplication」を選択します。
            MavenテストやJUnitの実行構成ではありません。

        (3) 通常起動用の構成であることを確認します。
            今回は test プロファイルを有効にしません。

        (4) 「環境」タブで、次の環境変数が設定済みか確認します。

            KEEPIA_DB_PASSWORD
                PostgreSQLへの接続パスワード

            KEEPIA_LOGIN_KEY_SECRET
                すでに設定したログイン試行管理用の秘密鍵

            実際のパスワードや秘密鍵は、この手順書に記録しません。

        (5) ブロック解除の待ち時間を短くするため、次を一時追加します。

            変数名：KEEPIA_LOGIN_BLOCK_DURATION
            値    ：1m

            標準のブロック時間は30分です。
            今回は手動確認中だけ1分に変更します。

        (6) 「適用」→「実行」を押します。
            起動済みの場合は、一度停止してから起動し直します。

        (7) コンソールで起動完了を確認します。
            以下では、ポート番号を変更していない前提で説明します。

            http://localhost:8080/

    2.3 DBeaverで接続先を確認する
        (1) keepia に接続したSQLエディタを開きます。

        (2) 次のSQLだけを実行します。

            SELECT current_database();

        (3) 結果が keepia であることを確認します。

        SQLの実行方法
            Ctrl + Enter
                カーソル位置のSQLを1文実行します。
                各テスト中のUPDATEには、こちらを使用します。

            Alt + X
                SQLスクリプト全体を実行します。
                次の「2.4 テストデータの登録」に使用します。

        コミットについて
            自動コミットが無効な場合は、変更後にコミットしてください。
            コミット前の変更は、アプリケーション側に反映されません。

    2.4 テストデータを登録する
        以下をSQLエディタに貼り付け、スクリプト全体を実行します。
        自動コミットが無効な場合は、実行後にコミットします。

        -- 手動確認用の保守会社
        INSERT INTO tenants (id, name, status)
        VALUES (
            'f1000000-0000-0000-0000-000000000001',
            'Manual Test Tenant',
            'ACTIVE'
        )
        ON CONFLICT (id) DO NOTHING;

        -- 手動確認用の顧客
        INSERT INTO customers (
            id, tenant_id, name, contact_email, status
        )
        VALUES (
            'f2000000-0000-0000-0000-000000000001',
            'f1000000-0000-0000-0000-000000000001',
            'Manual Test Customer',
            'manual-contact@example.com',
            'ACTIVE'
        )
        ON CONFLICT (id) DO NOTHING;

        -- 手動確認用の管理者
        INSERT INTO app_users (
            id, tenant_id, customer_id, email,
            display_name, role, status, password_hash
        )
        VALUES (
            'f3000000-0000-0000-0000-000000000001',
            'f1000000-0000-0000-0000-000000000001',
            NULL,
            'manual-admin@example.com',
            'Manual Admin',
            'ADMIN',
            'ACTIVE',
            '$2a$10$6emdNeCFr3yolG2zB4vP0uDr8Ph8DLGpD66Cf54oaQsaudAXwBgLy'
        )
        ON CONFLICT (id) DO NOTHING;

        -- 手動確認用の顧客ユーザー
        INSERT INTO app_users (
            id, tenant_id, customer_id, email,
            display_name, role, status, password_hash
        )
        VALUES (
            'f3000000-0000-0000-0000-000000000002',
            'f1000000-0000-0000-0000-000000000001',
            'f2000000-0000-0000-0000-000000000001',
            'manual-customer@example.com',
            'Manual Customer',
            'CUSTOMER',
            'ACTIVE',
            '$2a$10$6emdNeCFr3yolG2zB4vP0uDr8Ph8DLGpD66Cf54oaQsaudAXwBgLy'
        )
        ON CONFLICT (id) DO NOTHING;

        再実行時の注意
            同じIDが存在する場合、その行は変更されません。
            途中で中断して再開する場合は、MT-05の復旧用SQLで
            対象をACTIVEに戻してから進めてください。

    2.5 使用するログイン情報
        管理者
            メールアドレス：manual-admin@example.com
            パスワード    ：ManualTest-2026!
            表示名        ：Manual Admin
            権限          ：ADMIN

        顧客ユーザー
            メールアドレス：manual-customer@example.com
            パスワード    ：ManualTest-2026!
            表示名        ：Manual Customer
            権限          ：CUSTOMER

        ここで使うのは、Keepia画面にログインするための情報です。
        PostgreSQLへの接続パスワードとは別のものです。


3. 手動テスト

    MT-01 ログイン画面を表示できる
        【操作】
            (1) ブラウザで次のURLを開きます。

                http://localhost:8080/login

        【期待結果】
            ・メールアドレスの入力欄が表示される。
            ・パスワードの入力欄が表示される。
            ・ログインボタンが表示される。


    MT-02 正しいメールアドレスとパスワードでログインできる
        【操作】
            (1) ログイン画面で次を入力します。

                メールアドレス：manual-admin@example.com
                パスワード    ：ManualTest-2026!

            (2) ログインボタンを押します。

        【期待結果】
            ・ホーム画面に移動する。
            ・利用者名「Manual Admin」が表示される。
            ・権限「ADMIN」が表示される。


    MT-03 誤った資格情報では共通エラーを表示する
        【操作】
            (1) ログイン中の場合は、先にログアウトします。

            (2) 次の情報でログインを試します。

                メールアドレス：manual-admin@example.com
                パスワード    ：wrong-password

            (3) 表示されたエラーメッセージを確認します。

            (4) 次の情報で、もう一度ログインを試します。

                メールアドレス：manual-missing@example.com
                パスワード    ：wrong-password

            (5) 2回のエラーメッセージを比較します。

        【期待結果】
            ・どちらの試行でもログインできない。
            ・どちらも同じ共通エラーメッセージが表示される。
            ・メールアドレスの登録有無を示すメッセージが出ない。

        【後処理】
            正しい管理者の情報でログインします。
            これにより、管理者のログイン失敗回数をリセットします。


    MT-04 ログアウトできる
        【操作】
            (1) 管理者としてログインした状態にします。

            (2) ホーム画面のログアウトボタンを押します。

            (3) ログイン画面への移動と、ログアウトの案内を確認します。

            (4) アドレスバーに次を入力して開きます。

                http://localhost:8080/

        【期待結果】
            ・ログアウト後はログイン画面に移動する。
            ・ホームURLを直接開いても、ログイン画面に戻される。

        【確認方法の補足】
            ブラウザの「戻る」だけではキャッシュが表示されることが
            あるため、ホームURLを直接開いて確認します。


    MT-05 停止利用者と停止所属先を拒否できる
        【共通の進め方】
            以下のA、B、Cを、それぞれ順番に実施します。
            停止用SQLと復旧用SQLを一括実行しないでください。
            各SQLを1文ずつ実行し、途中でブラウザを操作します。
            自動コミットが無効な場合は、各UPDATE後にコミットします。

        A. 利用者が停止された場合
            【操作】
                (1) 管理者でログインします。

                (2) DBeaverで次の停止用SQLを実行します。

                    UPDATE app_users
                    SET status = 'STOPPED'
                    WHERE email = 'manual-admin@example.com';

                (3) ブラウザでホーム画面を再読み込みします。

                (4) 正しい管理者の情報でログインを試します。

            【期待結果】
                ・ログイン中でも、再読み込み時にログイン画面に戻る。
                  URLは /login?expired になる。
                ・停止中は、正しい情報を入力してもログインできない。
                ・共通エラーメッセージが表示される。

            【復旧】
                (5) DBeaverで次の復旧用SQLを実行します。

                    UPDATE app_users
                    SET status = 'ACTIVE'
                    WHERE email = 'manual-admin@example.com';

                (6) 正しい管理者の情報で再度ログインします。
                    ログインできることを確認し、ログアウトします。

        B. 所属する保守会社が停止された場合
            【操作】
                (1) 管理者でログインします。

                (2) DBeaverで次の停止用SQLを実行します。

                    UPDATE tenants
                    SET status = 'STOPPED'
                    WHERE id = 'f1000000-0000-0000-0000-000000000001';

                (3) ブラウザでホーム画面を再読み込みします。

                (4) 正しい管理者の情報でログインを試します。

            【期待結果】
                ・再読み込み時に /login?expired に戻される。
                ・保守会社の停止中は、管理者もログインできない。
                ・共通エラーメッセージが表示される。

            【復旧】
                (5) DBeaverで次の復旧用SQLを実行します。

                    UPDATE tenants
                    SET status = 'ACTIVE'
                    WHERE id = 'f1000000-0000-0000-0000-000000000001';

                (6) 正しい管理者の情報で再度ログインします。
                    ログインできることを確認し、ログアウトします。

        C. 所属する顧客が停止された場合
            【操作】
                (1) 次の顧客ユーザーでログインします。

                    メールアドレス：manual-customer@example.com
                    パスワード    ：ManualTest-2026!

                (2) DBeaverで次の停止用SQLを実行します。

                    UPDATE customers
                    SET status = 'STOPPED'
                    WHERE id = 'f2000000-0000-0000-0000-000000000001';

                (3) ブラウザでホーム画面を再読み込みします。

                (4) 正しい顧客ユーザーの情報でログインを試します。

            【期待結果】
                ・再読み込み時に /login?expired に戻される。
                ・顧客の停止中は、その顧客ユーザーがログインできない。
                ・共通エラーメッセージが表示される。

            【復旧】
                (5) DBeaverで次の復旧用SQLを実行します。

                    UPDATE customers
                    SET status = 'ACTIVE'
                    WHERE id = 'f2000000-0000-0000-0000-000000000001';

                (6) 正しい顧客ユーザーの情報で再度ログインします。
                    ログインできることを確認し、ログアウトします。

            【対象ユーザーの補足】
                管理者は顧客に所属していないため、この確認では必ず
                manual-customer@example.com を使用してください。


    MT-06 403画面を表示できる
        【操作】
            (1) ブラウザで次のURLを開きます。

                http://localhost:8080/access-denied

            (2) 403画面の内容を確認します。

            (3) HTTPステータスも確認する場合は、F12キーで開発者
                ツールを開き、「Network」または「ネットワーク」を
                選択してから、画面を再読み込みします。
                一覧の access-denied のステータスを確認します。

        【期待結果】
            ・アクセスできない旨と、権限がない旨の案内が表示される。
            ・HTTPステータスが403になる。
            ・例外の詳細、SQL、内部クラス名などが画面に表示されない。

        【この確認だけでは判定できないこと】
            上記は403画面自体の確認です。
            権限不足の利用者が保護された業務URLへアクセスして403に
            なることは、対象URLの実装後に追加で手動確認します。
            現時点の記録は「対象URL未実装のため手動未実施」とします。


    MT-07 ログイン失敗上限到達後に一時ブロックされる
        【事前条件】
            ・2.2の環境変数でブロック時間を1mにして起動している。
            ・管理者、保守会社、顧客をACTIVEに戻している。
            ・同じブラウザ、同じ接続元で、localhostのURLを使用する。

        【操作】
            (1) 正しい管理者の情報で一度ログインし、ログアウトします。
                管理者の失敗回数をリセットするための操作です。

            (2) 次の情報で、ログインに5回連続で失敗します。

                メールアドレス：manual-admin@example.com
                パスワード    ：wrong-password

            (3) 5回目の失敗直後に、正しい情報でログインを試します。

                メールアドレス：manual-admin@example.com
                パスワード    ：ManualTest-2026!

        【期待結果：ブロック中】
            ・正しいパスワードでもログインできない。
            ・共通エラーメッセージが表示される。

        【DBでも状態を確認する場合】
            DBeaverで次のSQLを実行します。

            SELECT
                failure_count,
                blocked_until,
                CURRENT_TIMESTAMP AS checked_at
            FROM login_rate_limits
            ORDER BY updated_at DESC;

            直前の試行に対応する行について、失敗回数が5であることと、
            blocked_until が現在より後の時刻であることを確認します。
            複数行がある場合は、操作時刻と更新順を併せて確認します。
            メールアドレスはHMAC化されるため、平文では保存されません。

        【操作：解除後】
            (4) 5回目の失敗によるブロック開始から1分以上待ちます。

            (5) 正しい管理者の情報で、再度ログインを試します。

        【期待結果：解除後】
            ・ログインできる。
            ・ホーム画面が表示される。

        【記録】
            今回はブロック時間を1分に変更して確認したことを記録します。
            標準設定の30分を実際に待つ確認とは区別してください。


4. テスト後の後処理
    (1) MT-05で変更した利用者、保守会社、顧客が、すべてACTIVEに
        戻っていることを確認します。

    (2) ブラウザからログアウトします。

    (3) Eclipseの通常起動用実行構成を開き、「環境」タブから
        KEEPIA_LOGIN_BLOCK_DURATION を削除して「適用」を押します。
        既存のパスワードや秘密鍵の環境変数は残します。

    (4) アプリケーションを停止し、起動し直します。
        ブロック時間が標準設定の30分に戻ります。

    (5) 今回登録した手動確認用データは、再実施用として残せます。
